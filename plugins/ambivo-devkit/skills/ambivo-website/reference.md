# App Factory CMS reference

What a website on Ambivo is made of, and what the `website_*` tools accept. Read it before saving a
page. The tables between `BEGIN GENERATED` and `END GENERATED` are rebuilt from App Factory's own
definitions; the rest is written by hand from the same code.

## How a page is saved

A page is one document: `{slug, title, nav_label, show_in_nav, status, blocks, seo}`. Each block is
`{type, data}` plus optional presentation options (`background`, `padding`, ...).

`website_page_save` without `page_id` creates a page; with `page_id` it **replaces** the page. A
replace sets every field you leave out back to its default:

| Left out | Becomes | What happens |
|---|---|---|
| `slug` | `""` | The page tries to become the home page. It fails with "already exists" or takes the home address. |
| `status` | `"draft"` | The page leaves the live site at the next publish. |
| `blocks` | `[]` | The page is empty. |
| `seo` | `{}` | The page's search title and description are gone. |
| `nav_label`, `show_in_nav` | `""`, `true` | The menu label falls back to the title. |

So on every save:

1. Read the page with `website_page_get`.
2. Change what you need in that object.
3. Send all of `slug`, `title`, `nav_label`, `show_in_nav`, `status`, `blocks` and `seo` back.

A new page starts as `draft` unless you send `status: "published"`. The tool reads the page back and
compares each field you sent, except `slug`, which App Factory may normalize.

Block `data` is not checked on save. A wrong field name is stored without error and shows nothing on
the page, so use the names below exactly. An unknown block `type` is skipped when the page renders.
A block whose data makes its renderer fail (a form `fields` entry that is a string, for example) is
dropped from the page. Both are silent; check every page with `website_preview_link`.

### hero

The opening section of a page: the page's only `<h1>`, a line under it, an optional button and an optional background image. Use one per page, first.

| Field | Type | Required | Default when empty | Rules |
|---|---|---|---|---|
| `headline` | string | yes |  | Rendered as the page's `<h1>`. Plain text; HTML is escaped. |
| `subheadline` | string | no |  | The line under the headline. Plain text. |
| `cta_text` | string | no |  | Button label. No button when empty. |
| `cta_url` | string | no | `"#"` | Button link: a site path (`/contact`) or a full `https://` URL. |
| `image` | URL | no |  | Background image behind the hero. See Images. |

```json
{
  "type": "hero",
  "data": {
    "headline": "Fresh bread, baked every morning",
    "subheadline": "Order by 9 pm and collect it warm the next day.",
    "cta_text": "Order now",
    "cta_url": "/contact",
    "image": "https://example.com/images/shop-front.jpg"
  }
}
```

### rich_text

| Field | Type | Required | Default when empty | Rules |

### Text and escaping

Plain-text fields (headings, titles, labels, button text, captions) are HTML-escaped. Markup typed
there shows as text. Formatting goes in `rich_text.markdown`, `tabs` bodies and `accordion` answers
(Markdown), or in `rich_text.html` and `html` blocks (raw HTML, published unchanged).

Links ending in `.html` that match a published page (`about.html`, `../about.html`) are rewritten
to the page's address at publish. Other links are left as written.

A NUL character (`\u0000`) anywhere in a page stops the whole site from publishing.

### Slugs

- The home page has slug `""`. A page with slug `home` is also served at `/`; never have both.
- The page API lowercases the slug and trims `/` from both ends. It does not check the pattern above.
  Keep to it anyway: lowercase letters, digits and hyphens, with `/` for a nested page
  (`services/wedding-cakes`). A slug with spaces or other characters is stored and published as is.
- Two pages cannot share a slug. The save fails with "A page with slug '...' already exists" (409).
- `blog` and anything under `blog/` belong to the blog when it is on. Avoid them as page slugs.
- The site also publishes `sitemap.xml`, `robots.txt`, `llms.txt`, `feed.xml` (with a blog),
  `404.html`, `favicon.ico` and the folders `themes/` and `assets/`. Do not use these as slugs.

### Search and sharing

- Browser title: `seo.title`, else the page `title`, else the site name; then the site's
  `seo.title_suffix`.
- Description: `seo.description`, else the site's `seo.default_description`.
- Share image: `seo.og_image`, else the site's `seo.default_og_image`.
- Every page gets canonical, Open Graph and Twitter tags, and structured data: the organization
  (with `logo_url` and `seo.social_links`), the website on the home page, a breadcrumb on other
  pages, and an FAQ from `accordion` blocks.
- `sitemap.xml` lists published pages without `noindex`.
- On the preview address (`<name>.apps.ambivo.com`) every page is `noindex` and `robots.txt` blocks
  all crawlers, whatever the settings say. Search starts once the client's own domain is connected.

Write a `seo.title` under 60 characters and a `seo.description` of one or two plain sentences,
under 160 characters, for every page.

## Site settings

`website_settings` without `settings` reads them; with `settings` it changes the keys you send. Each
key you send **replaces** that whole key. Sending `{"seo": {"title_suffix": " | Hill Street
Bakery"}}` drops `default_description` and every other `seo` field. Read the settings first, change
the object, and send the whole key back. The same goes for `nav`, `design_tokens` and `analytics`.

## Navigation

- `nav.header` empty: the header menu is built from published pages with `show_in_nav: true`,
  sorted by title A to Z, each labelled `nav_label` or `title`, plus "Blog" when the blog is on. The
  home page sorts by its title like any other.
- `nav.header` set: exactly those items, in that order. Use this for a deliberate order
  (Home, Services, About, Contact).
- `nav.footer`: items shown as links in the footer. Nothing is added automatically.
- The theme shows top-level items only; `children` are stored and not shown.
- On a phone the header collapses behind a menu button.

```json
{"nav": {"header": [{"label": "Home", "url": "/"}, {"label": "Services", "url": "/services"},
                    {"label": "About", "url": "/about"}, {"label": "Contact", "url": "/contact"}],
         "footer": [{"label": "Privacy", "url": "/privacy"}]}}
```

## Redirects

`redirects: [{"from_path": "/old-page", "to_path": "/new-page"}]` in settings. At publish each one
becomes a small page at the old path that sends visitors on (meta refresh and a link, marked
noindex). A redirect whose `from_path` is a published page is skipped; the page wins. `from_path`
must start with `/`. Only exact paths work here: a `/*` wildcard is not expanded.

## Forms

The `form` block posts to App Factory's form intake for the site. A submission stores `form_key`,
the field values by `name`, the time, the visitor's IP address and browser. The visitor sees
"Thanks! We will be in touch." or "Something went wrong." (fixed text).

- Submissions are read in the site editor (Submissions page; managers and admins). The newest 500
  are listed.
- No email is sent and no CRM lead is made. To put a lead into the client's Ambivo CRM, use an
  `ambivo_widget` block with one of the client's Ambivo form widgets instead.
- There is no spam check or captcha on the `form` block.
- In a preview the form does not submit anywhere real. Test a form only on the published site.
- A handover deletes every stored submission. Do not leave test submissions you need.
- A `<form>` inside an `html` block is caught and posted to the same intake, but its values are sent
  in a shape the intake does not read: the submission is stored with no fields. Use the `form` block.

## Images and media

The `website_*` tools cannot upload files. An image gets into a block as a URL:

1. The user gives you an image address on the web (their existing site, a CDN). Use `https://`.
2. Or the client uploads the image in the site editor's **Media** page and copies its address. The
   page editor's image fields also have a **Browse** button that uploads and picks.
3. Never invent an image URL, and never use an image the client has no right to use. Without real
   images, build the page from text blocks.

Image fields: `hero.image`, `image.src`, `gallery.items[].src`, `carousel.items[].src`,
`background_image` (with `background: "image"`), `seo.og_image`, `seo.default_og_image`,
`logo_url`, `favicon_url`. No field checks the host, size or type; the visitor's browser loads the
URL as given. Keep files small (under about 500 KB for photos) and give every image `alt` text.

The media library accepts the types and size in Limits. Uploaded files get a permanent public
address on Ambivo's media host.

## Preview, publish and restore

- **Saving** a page or settings changes the stored content only. The live site does not change.
- **`website_preview_link`** renders one page from the stored content, drafts included, with
  `noindex`. `custom_scripts`, `head_html` and `body_html` are left out of previews. The link holds
  a token that lasts 12 hours; share it only with people who may see drafts.
- **`website_publish`** (manager or admin) renders every `published` page and the settings, uploads
  the whole site and removes files that are no longer part of it, so a page made `draft` disappears.
  Then it saves a restore point of all pages, posts and settings (only when something changed since
  the last one). The answer has the site URL and the restore point.
- A publish is refused when Ambivo has taken the site offline, or when stored text is damaged
  (it names the pages; restore an earlier revision of each and publish again).
- **Restore** is not a `website_*` tool. In the site editor:
  - every page save keeps the page's previous version (see Limits for how many). The visual
    editor's **Undo** puts the last one back in the stored page; publish to put it live. The state
    before the undo is kept too.
  - **Versions** (manager or admin) puts the whole site back as it was at one publish, including
    pages deleted since, and publishes it at once. Current content, drafts included, is saved as a
    backup version first.
- The editor's **Changes** page lists what the next publish would change, page by page.

## When a save is refused

| Answer | Cause | What to do |
|---|---|---|
| 401 "Not authenticated" / "You no longer have access to this site." | The CMS session ended or the person was removed | The tool gets a fresh session once by itself; if it still fails, sign in again |
| 403 "This account has no access to this site yet..." | The signed-in person is not the owner and has no invite | Ask a site admin to invite them |
| 403 "Only a manager or admin can do this." | Role too low | Pages need editor; publish, settings and page delete need manager |
| 403 "This site belongs to a different company." | Signed in to another company | Sign in to the company that owns the site |
| 404 "Not found" | Wrong `page_id` | List pages with `website_pages` |
| 409 "A page with slug '...' already exists" | Duplicate slug, often a replace sent without `slug` | Send the page's own slug |
| 422 | A field has the wrong type (`show_in_nav` not a boolean, `blocks` not a list, no `title`) | Fix the type |
| 400 (settings) | An analytics id is not usable; the message says what to paste | Fix the value |
| 500 "The save did not store correctly..." | The stored copy did not match after several tries | Save again |
| `READ_BACK_DIFFERS` (from the tool) | The stored page differs from what was sent | Save again; never assume it worked |
| 409 at publish | Site taken offline by Ambivo, or damaged text | See Preview, publish and restore |

No size limit is checked on a page. Keep a page's HTML and text reasonable; a very large page is
slow for visitors.

## What the client can change later

After the handover the client edits the site in Ambivo's site editor, with the role their invite
gives them (editor: pages and drafts; manager: also publish, settings, submissions, versions,
deleting pages and media; admin: also people). They can:

- edit pages in the block form (the blocks marked below), or in the visual editor, which moves,
  removes, duplicates and inserts sections and edits `html` blocks in place;
- change a page's title, slug, menu label, status and search title and description;
- add and remove pages; write blog posts when the blog is on;
- change the theme, colors, fonts, corner shape, width, custom CSS, tracking ids and verification
  codes (Appearance);
- edit the header and footer menus and the redirects (Navigation);
- upload images (Media), read form submissions, check the sitemap, see pending changes, publish,
  and restore pages or whole versions;
- invite people and set roles.

## Blog posts

App Factory sites can have a blog (`/blog`, tag pages, `feed.xml`), but the `website_*` tools do not

site editor.
